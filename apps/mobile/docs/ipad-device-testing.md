# Running the mobile app on a physical iPad

`apps/mobile` on real hardware, as opposed to the simulator. The simulator path
needs almost none of this — everything here exists because a physical device
requires code signing, and because several of the failures look identical to one
another while needing opposite fixes.

Keep machine-specific values (team id, device UDID, vault paths, hostnames) in
`.env.local` and in a personal `*.local.md` note, both gitignored. This document
stays generic so it is useful to anyone.

> The mobile app lives only on `mobile-ui-foundation`. `apps/` is not on `main`
> or any release tag, so checking out a tag removes the whole app from the
> working tree.

---

## 1. One-time setup

### Toolchain

Full Xcode is required — Command Line Tools are not enough. If `xcode-select`
points at CLT you do not need `sudo`; exporting the path is sufficient:

```bash
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
```

CocoaPods must be installed (`brew install cocoapods`).

### Signing

A **free** Apple ID is enough to run on your own devices. The paid programme is
only required for distribution, despite what most signing documentation implies.
Add the account in Xcode ▸ Settings ▸ Accounts — this needs your password and
cannot be scripted.

Then read the team id:

```bash
pnpm mobile:ios:team
```

The team id is the **`OU` field** of the signing certificate, *not* the
parenthesised id in its common name. Both are ten characters, so they are easy
to confuse, and only the OU resolves a provisioning profile:

```
CN=Apple Development: you@example.com (AAAAAAAAAA)   ← certificate id, wrong
OU=BBBBBBBBBB                                        ← team id, correct
```

Record it in `.env.local` at the repo root (gitignored, so it survives updates
pulled from upstream):

```
APPLE_DEVELOPMENT_TEAM=<your team id>
```

### On the iPad

- Enable Developer Mode: Settings ▸ Privacy & Security ▸ Developer Mode
- Pair with the Mac and trust it
- After the first install, trust the certificate:
  **Settings ▸ General ▸ VPN & Device Management ▸ Apple Development: … ▸ Trust**

The iPad needs internet access at that moment — it verifies the certificate
online. One trusted certificate covers every app signed by that team, so this is
once per device, not once per app.

## 2. Everyday flow

```bash
pnpm mobile:ios:check     # prerequisites only, changes nothing
pnpm mobile:ios:device    # build, install and launch on the attached iPad
```

The build is **Release**, so the JS bundle is embedded and the app runs with no
Metro server on the Mac.

`apps/mobile/ios` is generated by `expo prebuild` and is not committed, so a
regeneration silently drops anything configured inside it. The script therefore
re-applies three things on every run:

| Re-applied each run | Why |
| --- | --- |
| `DEVELOPMENT_TEAM` in the Xcode project | prebuild regenerates `project.pbxproj` |
| `NODE_BINARY` in `.xcode.env.local` | a versioned Homebrew Cellar path breaks at the next `brew upgrade node` |
| ATS exception for the dev-vault host | prebuild regenerates `Info.plist` |

It also defaults `SENTRY_DISABLE_AUTO_UPLOAD=true`. The Release build uploads
source maps to Sentry and fails without `SENTRY_ORG`, `SENTRY_PROJECT` and a
token; a personal device build has no Sentry project. Set the variable to
`false` yourself to upload.

### After pulling a large upstream update

`apps/mobile/ios` is built for the Expo and React Native versions that were
installed when it was generated. After an update that moves either, regenerate
it before building:

```bash
pnpm install --frozen-lockfile
cd apps/mobile && pnpm exec expo prebuild -p ios --clean
```

The first `pod install` after a clean prebuild takes several minutes. The Xcode
scheme follows the app name in `app.json`; if upstream renames the app, update
`SCHEME` in `scripts/ios-device.sh` to match.

## 3. Failures and what they actually mean

### Build fails at signing — "PLA Update available"

```
error: Unable to process request - PLA Update available: You currently don't
have access to this membership resource.
error: No profiles for '<bundle id>' were found
```

Apple has published a new Program License Agreement and will not issue a
provisioning profile until it is accepted. There is no dialog in Xcode. Sign in
at developer.apple.com/account as the **Account Holder** of the signing team,
select that team, and accept the agreement from the banner on the Account page.
The second error is a consequence of the first and clears with it. A machine
that already holds a valid cached profile keeps building, so this tends to
appear on a new Mac.

### Installs, then refuses to launch — "not been explicitly trusted"

```
Unable to launch … because it has an invalid code signature, inadequate
entitlements or its profile has not been explicitly trusted by the user
```

Do the Trust step above. No code change removes this; it is a per-device,
per-certificate gate enforced by iOS.

### Installs, then refuses to launch — "could not be, unlocked"

The device is locked. iOS checks this *before* the signature, so a locked iPad
and an untrusted certificate produce near-identical refusals but need opposite
actions. Unlock the device and re-run.

### Build fails in the Hermes script phase

```
…/Script-….sh: line 9: /opt/homebrew/Cellar/node/<version>/bin/node: No such file
```

A stale `NODE_BINARY` in `apps/mobile/ios/.xcode.env.local` pinned to a Homebrew
version that no longer exists. Point it at the stable symlink
(`/opt/homebrew/bin/node`); the build script does this automatically.

### Build fails while bundling JS

```
Cannot find module '@babel/plugin-transform-react-jsx'
```

A preset requests it by name, and pnpm's strict layout leaves it unresolvable
from `apps/mobile` unless declared there. Debug builds never hit this because
Metro bundles at runtime rather than during the build — it only appears in
Release.

### Build fails in the Sentry upload phase

```
error: An organization ID or slug is required (provide with --org)
```

The build was started without the script, or with
`SENTRY_DISABLE_AUTO_UPLOAD=false` and no Sentry credentials. Use
`pnpm mobile:ios:device`, which skips the upload by default.

### Launches, then dies within a second

`devicectl` still reports "launched". Confirm the process and read the crash
report as described in the next section. APIs compiled only for the simulator
are the usual cause: one guarded by `TARGET_OS_SIMULATOR` returns `nil` on a
device, and an unannotated Objective-C return is imported into Swift implicitly
unwrapped, so calling through it traps rather than failing softly.

## 4. Diagnosing a crash on the device

`devicectl` reports "launched" even when the process dies immediately, so
confirm separately:

```bash
# still running?
xcrun devicectl device info processes --device <UDID> | grep <AppName>

# stream stdout/stderr until it exits
xcrun devicectl device process launch --device <UDID> --console \
  --terminate-existing <bundle-id>
```

For a stack trace, pull the crash report off the device with
[libimobiledevice](https://libimobiledevice.org):

```bash
idevicecrashreport -u <UDID> -e ./crash
```

An `.ips` is a JSON header line followed by a JSON body, so read the triggered
thread like this:

```bash
python3 -c "
import json,glob
d=json.loads(open(sorted(glob.glob('crash/<AppName>-*.ips'))[-1]).read().split('\n',1)[1])
imgs=d['usedImages']
th=[t for t in d['threads'] if t.get('triggered')][0]
print(d['exception'])
for f in th['frames'][:12]:
    print(' ', imgs[f['imageIndex']].get('name'), f.get('symbol'))
"
```

`idevicescreenshot` does not work alongside `devicectl` — it expects a developer
disk image mounted the older way.

## 5. Reading a real vault instead of fixtures

The default workspace source is the bundled **fixtures**. To read a real vault,
run the dev-vault bridge on your machine and point the app at it.

`apps/mobile/.env.local` (gitignored; Expo loads it from the app root):

```
EXPO_PUBLIC_TOLARIA_WORKSPACE_SOURCE=dev-vault
EXPO_PUBLIC_TOLARIA_DEV_VAULT_URL=http://<host>:8765
MOBILE_DEV_VAULT_PATH=/absolute/path/to/vault
```

```bash
pnpm mobile:dev-vault      # serves the vault; binds 0.0.0.0
pnpm mobile:ios:device     # rebuild so the URL is compiled in
```

On a device the URL cannot be `localhost`. Over Tailscale, prefer the MagicDNS
name (`<machine>.<tailnet>.ts.net`) over the `100.x` address: it survives a node
re-registration and resolves on any device signed into the tailnet.

Four things each break this silently:

1. **`EXPO_PUBLIC_*` are compile-time.** Editing `.env.local` requires a
   rebuild, not just a relaunch.
2. **They are only inlined where referenced literally.** The `envValue()`
   helpers in `src/screens/MobileUiLab.tsx` and
   `src/screens/mobileUiWorkspaceSourceRequest.ts` read `process.env[name]`, a
   computed lookup that Babel does not substitute, so the values are `null` on a
   device. `src/screens/inlinedEnv.ts` names each variable explicitly and both
   helpers fall back to it — add any new variable there, and give any new
   `envValue()` the same fallback, or it will read as unset.
3. **App Transport Security blocks cleartext HTTP.** `NSAllowsLocalNetworking`
   covers `.local` and link-local addresses only; a `.ts.net` name does not
   qualify, so an `http://` bridge is refused *before a socket opens*. That is
   indistinguishable from the server being down — no connection, nothing on the
   wire. The build script adds a host-scoped exception derived from the
   configured URL. Serving the bridge over HTTPS would remove the need for it.

4. **The bridge URL must be on a private network.**
   `src/workspace/devVaultBridgeUrl.ts` rejects any other host before a request
   is made, which shows an error screen with nothing on the wire. It accepts
   `localhost`, `.local` names, RFC 1918 addresses, `.ts.net` names and the
   `100.64.0.0/10` range Tailscale assigns from. A public hostname is refused by
   design.

### Confirming the device actually fetched

```bash
lsof -nP -i TCP:8765 | grep ESTABLISHED
```

An established connection from the device's address is proof; a running app is
not, since it renders a status screen when the fetch fails. The connection
lasts only as long as the download, so watch in a loop while relaunching the
app rather than checking once afterwards.

### Limits of the bridge

- **Read-only** — it serves `GET /snapshot` and `GET /health`, so edits made on
  the device have nowhere to go.
- **The whole vault in one uncompressed response.** Fine on a LAN; slow over a
  relayed link.
- The serving machine must be awake with the bridge running. It is a foreground
  process and does not survive a restart.
- The bridge always binds `0.0.0.0`. `MOBILE_DEV_VAULT_HOST` only changes the
  address printed at startup, which otherwise reads `127.0.0.1`.

## 6. Known limits on a free Personal Team

- **Provisioning profiles last 7 days.** The app stops launching afterwards;
  re-run `pnpm mobile:ios:device` to rebuild and reinstall. A paid membership
  gets a one-year profile; the script prints the expiry after each install.
